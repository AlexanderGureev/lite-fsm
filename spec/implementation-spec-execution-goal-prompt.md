# Implementation Spec Execution Goal Prompt

Запусти это как цель для агента-оркестратора.

## Параметры

- ТЗ: `spec/spec.md`
- Журнал: `spec/spec-log.md`

Если пользователь передал другие пути, используй их.

## Цель

Выполнить ТЗ, оформленное по `implementation-spec`, строго по этапам ТЗ и состоянию журнала. Оркестратор владеет порядком работ, восстановлением состояния, dispatch одного этапа, ревью, проверками, обновлением журнала и финальным readiness gate.

Этап нельзя закрыть по отчету исполнителя — только после ревью, проверок и записи в журнал.

## Глоссарий

- Чистый подагент — новая сессия без истории прошлых этапов. Допустимый контекст: системные инструкции среды, ближайшие `AGENTS.md`, активные ТЗ и журнал, baseline этапа, текущее состояние active scope (включая уже сделанную stage-owned delta при продолжении этапа), brief текущего этапа.
- `executor-id` — стабильный handle (`subagent id`/`thread id`/`conversation id`), который платформа возвращает при создании подагента. Чистота гарантируется тем, что оркестратор создал подагента в текущем dispatch, а не пост-фактум проверкой.
- baseline — снимок рабочего дерева до первого dispatch этапа: `git status --short` (включая untracked), `git diff`, `git diff --staged`, active write scope и отмеченные чужие/out-of-scope изменения. Фиксируется один раз на этап и не меняется на corrective-итерациях и при смене исполнителя.
- stage-owned delta — изменения текущего этапа: текущий дифф минус baseline. baseline — канон для ее расчета.
- corrective-итерация — возврат `return_to_subagent` тому же исполнителю для фикса замечаний. Лимит 3 на этап; счетчик хранится в журнале.
- смена исполнителя — создание нового чистого подагента для незавершенного этапа, когда прежний недоступен. Не сбрасывает baseline и счетчик corrective; фиксируется причина; новый исполнитель получает существующую stage-owned delta как входное состояние.

## Инварианты

Safety (нарушение блокирует работу):

- У этапа в каждый момент один активный исполнитель. Подагент не переиспользуется для другого этапа; тому же исполнителю дают только corrective brief по его этапу. Нового чистого исполнителя для незавершенного этапа создают только при потере прежнего, с записью причины.
- Журнал реализации редактирует только оркестратор.
- Не откатывай и не перезаписывай чужие и out-of-scope изменения.
- Работай строго последовательно: один активный этап, один активный исполнитель, один review loop. Параллельные подагенты или этапы запрещены.
- Запрещенные build-команды из `AGENTS.md` или ТЗ не запускай.

Состояние:

- Журнал — единственный источник истины. Любой факт для восстановления (этап, статус, `executor-id`, baseline, delta, счетчик corrective, вердикт) пиши в журнал до соответствующего действия (write-ahead). Восстановление должно быть возможно из ТЗ и журнала без истории чата.
- Приоритет при конфликте: `AGENTS.md` (вложенные приоритетнее) и запреты команд → этот промт (процесс) → ТЗ (контракт) → журнал (состояние). Неразрешимый конфликт → blocker и решение пользователя.

Процесс:

- Перед продолжением всегда читай ближайшие `AGENTS.md`, ТЗ, журнал и текущее состояние дерева.
- Если платформа не возвращает стабильный `executor-id` при создании — этап не dispatch-ится, фиксируется blocker.
- Исполнитель вносит только точечные правки в active scope. Repo-wide операции (formatter/linter `--fix`, codemod, массовый рефактор), затрагивающие чужое или out-of-scope, запрещены.
- Этапы закрываются строго по порядку ТЗ: не начинай и не выбирай этап, пока все предыдущие не `done`.
- Не прерывай активного исполнителя, жди его ответа; подагенты могут работать долго.
- Cleanup/refactor этап обязателен и идет до финальной проверки; финальная проверка не заменяет stage gate этапа.

## Рабочий цикл

Повторяй, пока все этапы не `done` или работа не упрется в реальный `blocked`. Каждый шаг: Pre (предусловие) / Do (действия) / Out (результат).

### 1. Restore and Select

Pre: доступны ТЗ и журнал.

Do:

- Прочитай ТЗ и журнал полностью; сними текущее состояние дерева (`git status --short`, `git diff`, `git diff --staged`).
- Целостность журнала: более одного `in progress` или расхождение порядка этапов между ТЗ и журналом → blocker, реализацию не начинай.
- Выбери самый ранний не-`done` этап по порядку ТЗ. `not started` нельзя выбрать, если есть более ранний незакрытый (`in progress`/`blocked`).
  - Самый ранний незакрытый `blocked`: продолжай только при новом evidence или решении пользователя; иначе остановись на нем и эскалируй — не переходи к следующему этапу.
  - Самый ранний незакрытый `in progress`: восстанови (см. ниже).
  - Иначе первый `not started` (все предыдущие `done`): это новый этап.
- Восстановление `in progress`:
  - Ревалидируй baseline: текущее дерево должно быть совместимо с записанным baseline. При расхождении → зафиксируй риск или blocker, delta не считай по устаревшему baseline.
  - Если в журнале нет финального `accept`, повтори ревью и Verify существующей delta (идемпотентно) — не передиспатчивай нового исполнителя и не переписывай delta только из-за того, что вердикт не сохранился.
  - Если нужна доработка реализации, а прежний исполнитель недоступен: выполни смену исполнителя (шаг 2) для продолжения этапа, не сбрасывая baseline, delta и счетчик corrective.
- Чужой или пользовательский diff не трогай, учти его в write scope.

Out: строка `Restore: этап N — <название>, статус, исполнитель=<id|нет>, corrective=<N/3|—>, baseline=<ok|устарел|нет>, следующее действие`.

### 2. Prepare and Dispatch

Pre: этап выбран по правилам шага 1.

Do, строго в этом порядке:

1. Зафиксируй baseline этапа, если этап новый. Для продолжения, corrective или смены исполнителя используй уже зафиксированный baseline.
2. Создай нового чистого подагента и получи `executor-id`. Нет стабильного id → не dispatch; новый этап → `blocked`, незавершенный остается `in progress` с записью причины.
3. Запиши в журнал (write-ahead): `in progress`, baseline, `executor-id`, счетчик corrective.
4. Выдай подагенту (максимально доступный на платформе уровень рассуждения) self-contained brief по шаблону «Brief для исполнителя» — только активный этап. Не сокращай active scope, stage gate, запреты, совместимость, baseline и формат отчета. Для продолжения или corrective укажи, что уже сделано и что доделать.

Out: исполнитель работает в текущем worktree (читает код и тесты, реализует только активный этап, добавляет тесты, журнал не трогает) и возвращает `ready_for_review` или `blocked`.

### 3. Review (review gate)

Pre: получен `ready_for_review`.

Do:

- Сверь с контрактом активного этапа и с ТЗ: общие инварианты, матрица проверок, критерий полной готовности.
- Проверь весь diff, stage-owned delta относительно baseline, добавленные или измененные тесты и затронутые public exports, runtime contracts, storage schema, env/config, docs, examples.
- Прогони quality gates:
  - Traceability: каждый обязательный пункт этапа реализован, покрыт тестом или заблокирован с evidence.
  - Stage boundary: diff не реализует будущие этапы и не меняет out-of-scope поведение.
  - Delta ownership: изменения этапа отделены от baseline; чужие и out-of-scope не переписаны и не включены в acceptance.
  - Architecture: сохранены владельцы слоев и контрактов; нет дублирования validation, normalization, mapping, lifecycle state, diagnostics.
  - Public API: exports, types, routes, commands, env names, error semantics, compatibility rules совпадают с ТЗ.
  - Runtime behavior: порядок фаз, idempotency, rollback/atomicity, serialization/restore и side effects соблюдены.
  - No hacks: нет temporary helpers, transitional branches, debug logging, TODO/FIXME, dead code, silent fallback, sleep-based logic, необоснованных `any`/casts, hardcoded production assumptions, bypass для тестов.
  - Tests: проверяют observable behavior или static contract, а не только рендер, mock call, snapshot или детали реализации.
  - Negative and edge cases: обязательные ошибки, конфликты, legacy cases, empty states, boundary conditions покрыты, если входят в этап.
  - Coverage: configured threshold выполнен для затронутого scope; active production logic не исключена ради прохождения gate.
  - Docs/examples: публичное поведение обновлено, если этап меняет contract surface.
  - Generated files: не редактировались вручную при наличии source schema или команды генерации.
- Спорные gates (No hacks, Tests, Coverage, Delta ownership, Stage boundary) подкрепляй evidence (файл/строка, имя теста, команда с результатом); без evidence gate считается незакрытым.

Out (review gate):

- `pass` — статические gates закрыты с evidence; перейти к Verify.
- `return_to_subagent` — исправимые статические замечания (см. правило corrective).
- `blocked` — реальный блокер без решения пользователя или внешнего изменения.

### 4. Verify (verify gate)

Pre: review gate = `pass`.

Do: запусти разрешенные проверки из `Тесты этапа` и `Критерий завершения` по матрице:

- Behavior changes: focused behavior tests, relevant unit/integration tests, lint/type checks по ТЗ.
- Public types/exports: type/static tests и разрешенная проверка типов.
- Docs-only: source/docs audit и `git diff --check`.
- Cleanup/refactor: focused regressions, lint, `git diff --check`, source audit по stale identifiers.

Правила:

- Запрещенную build-команду не запускай — запиши точную команду для пользователя или CI.
- Прогон должен быть безопасен для повтора (идемпотентен); если проверка имеет необратимые side effects, отметь это.
- Инфраструктурный сбой (sandbox/network) → повтори по правилам среды с escalation.
- Невозможно запустить обязательную для gate проверку: → `blocked`. Перевод в `done` с риском допустим, только если ТЗ явно делегирует эту проверку пользователю/CI.

Out (итоговый verdict):

- `accept` — review gate `pass` и все обязательные проверки прошли.
- `return_to_subagent` — контентный провал проверки (см. правило corrective).
- `blocked` — провал, не закрываемый без решения пользователя или внешнего изменения.

Правило corrective и смены исполнителя (для `return_to_subagent` из шагов 3 и 4):

- Возврат идет тому же исполнителю, только по текущему этапу; счетчик corrective инкрементится в журнале. Лимит 3 итерации на этап.
- Исчерпан лимит или деградация исполнителя → `blocked` и решение пользователя.
- Исполнитель недоступен, но нужна доработка и лимит не исчерпан → смена исполнителя (шаг 2): новый чистый подагент продолжает этап с тем же baseline, delta и счетчиком. baseline на возвратах не пересчитывается.

### 5. Log Transition

Pre: есть итоговый verdict и результаты проверок.

Do: обнови журнал короткой записью по шаблону записи журнала. Поля: статус; `executor-id`; baseline и stage-owned delta без полного diff; счетчик corrective; смена исполнителя и причина, если была; scope; ключевые файлы или модули; команды и результат; coverage или почему не применимо; риски, blockers или expected remaining audit hits; следующее действие. Не вставляй полный diff, длинный вывод команд или рассуждения.

Out: статус переведен — `accept` → `done`; `return_to_subagent` → остается `in progress` (счетчик corrective обновлен); подтвержденный блокер → `blocked`.

### 6. Final Readiness Gate

Pre: все этапы, включая cleanup/refactor, имеют статус `done`.

Do:

- Запусти сквозную регрессию на интегрированном результате (обязательные тесты, lint/type checks, source audits), а не доверяй только записям этапов: поздний этап мог сломать ранний. Запрещенные build-команды не запускай — укажи их для пользователя/CI.
- Проверь критерий полной готовности из ТЗ и traceability всех этапов.
- Проверь отсутствие незакрытых `blocked`, TODO/FIXME, temporary branches, stale docs в active scope.
- Проверь, что каждый этап имеет уникальный `executor-id`, baseline и stage-owned delta в журнале.
- Проверь, что запрещенные build-команды агентом не запускались, а команды для user/CI build verification перечислены точно.

Out: финальная запись журнала с итоговыми gates, coverage, audit scope и residual risks.

## State Machine журнала

Статусы: `not started`, `in progress`, `done`, `blocked`.

| Переход                      | Кто делает  | Условие                                                                              |
| ---------------------------- | ----------- | ------------------------------------------------------------------------------------ |
| `not started -> in progress` | Оркестратор | Этап выбран, baseline зафиксирован, новый чистый исполнитель создан и его id записан |
| `not started -> blocked`     | Оркестратор | Dispatch невозможен: нельзя создать нового чистого исполнителя или получить его id   |
| `in progress -> done`        | Оркестратор | Review gate `pass` и verify gate `accept`: stage gate и проверки закрыты             |
| `in progress -> blocked`     | Оркестратор | Подтвержден блокер или исчерпан лимит corrective (правило шага 4)                    |
| `blocked -> in progress`     | Оркестратор | Есть новое evidence или решение пользователя                                         |
| `in progress -> not started` | Оркестратор | Recovery: исполнитель не был создан, stage-owned delta отсутствует, причина записана |

Смена исполнителя не меняет статус: этап остается `in progress`, обновляются только `executor-id` и причина. `done` не переводится назад без явного решения пользователя.

## Brief для исполнителя

```md
Рабочая директория: /path/to/repo

Реализуй один этап ТЗ: <path-to-spec>.
Журнал: <path-to-log>.

Этап: Этап N — <название>
Статус в журнале: `in progress`
Исполнитель: <executor-id>
Baseline рабочего дерева: <status/file-list/scope summary>
Продолжение этапа: <нет | да: что уже сделано и что доделать; corrective-итерация N/3, если это возврат>

Ты не один в рабочем дереве: не откатывай и не перезаписывай чужие изменения. Вноси только точечные правки в active scope; не запускай repo-wide formatter/linter `--fix`, codemod или массовый рефактор, которые затрагивают файлы вне active scope.
Журнал реализации не редактируй.
Ты создан только для этого этапа. Не выполняй другие этапы. После отчета принимай только corrective brief по этому же этапу.

Перед началом:

- Прочитай ближайшие `AGENTS.md`.
- Прочитай раздел ТЗ для активного этапа, общие инварианты, матрицу проверок и критерий полной готовности.
- Осмотри существующий код в active scope и ближайшие тесты.

Scope:

- Изменять: <файлы/packages/модули>.
- Не менять: <out-of-scope и будущие этапы>.
- Сохранять совместимость: <public API/error/storage/behavior guarantees>.

Implementation:

- Реализуй только контракт активного этапа.
- Не добавляй abstractions/helpers без второго места использования или явного снижения сложности.
- Не дублируй validation, normalization, mapping, lifecycle state или diagnostics между слоями.
- Сначала валидируй входные данные, затем transform, затем mutate/commit.
- Не оставляй TODO/FIXME, debug logging, dead code, temporary branches или bypass для тестов.

Tests and verification:

- Добавь или обнови тесты из `Тесты этапа`.
- Тесты должны проверять нужный contract outcome, включая negative/edge cases, если они применимы.
- Запусти разрешенные проверки из `Критерий завершения`.
- Запрещенные build-команды не запускай; укажи их в отчете как проверки для пользователя/CI.

Report:

- Status: `ready_for_review` или `blocked`.
- Исполнитель: <executor-id>.
- Baseline/delta: <что было до dispatch и какие stage-owned изменения добавлены>.
- Измененные файлы.
- Какие контракты этапа закрыты.
- Какие тесты добавлены/обновлены и что они проверяют.
- Команды и результат.
- Coverage status.
- Риски, assumptions, unresolved questions.
```

## Review Verdict

```md
Review verdict: <accept|return_to_subagent|blocked>

- Этап: Этап N — <название>
- Исполнитель: <executor-id>
- Corrective: <N/3>
- Baseline/delta: <что было до dispatch и какие stage-owned изменения добавлены>
- Измененные файлы: <список>
- Закрытые контракты: <кратко>
- Тесты: <что проверяют и результат>
- Review gate: <pass|return_to_subagent|blocked>
- Verify gate: <accept|return_to_subagent|blocked|not run>
- Architecture gate: <ok|issue>
- Scope gate: <ok|issue>
- Delta ownership gate: <ok|issue>
- No-hacks gate: <ok|issue>
- Coverage gate: <ok|issue|not applicable>
- Команды: <команды и результат>
- Риски/assumptions: <кратко>
```

Если verdict `return_to_subagent`, добавь corrective brief тому же `<executor-id>`: какие bullets не закрыты, какие тесты поверхностные или неверные, где нарушены architecture/scope/delta ownership gates, какие temporary решения убрать и какие проверки повторить. Нового подагента создавай только при смене исполнителя; лимит и эскалация — по правилу corrective из шага 4.

## Финальный результат

Когда цель завершена или остановлена по блокеру, дай короткий отчет:

- какие этапы выполнены;
- какие проверки запускались;
- какие build-проверки не запускались из-за запрета и какую команду должен выполнить пользователь/CI;
- какие риски остались;
- где обновлен журнал.
